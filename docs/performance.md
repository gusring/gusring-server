# 성능 측정

## 통계 API (2026-11-03)

목표: 이용 기록 100만 건(1년치)에서 통계 API 각 1초 안.

환경: 개발 PC의 Docker PostgreSQL 17.6 (기본 설정, work_mem 4MB), 서버는 로컬 `node --import tsx`.
NAS는 이보다 느릴 수 있어 배포 뒤 다시 잰다.

데이터 (`usage_event` 100만 행, 178MB):

- 현실 분포: 방문 66,667번 × 방문당 이벤트 15개, 방문자 2만 명 → (방문자, 날짜) 쌍 66,702개
- 최악 분포: 이벤트마다 시각 무작위, 방문자 5만 명 → (방문자, 날짜) 쌍 97만 개. 날짜별 방문자 중복 제거가 가장 무거운 경우

응답 시간 (5번 중 가장 느린 값, 초):

| API | 현실 30일 | 현실 366일 | 최악 30일 | 최악 366일 |
| --- | --- | --- | --- | --- |
| summary | 0.08 | 0.49 | 0.07 | 0.32 |
| forms | 0.04 | 0.06 | 0.03 | 0.06 |
| daily | 0.05 | 0.38 | 0.09 | 1.33 |
| search | 0.03 | 0.06 | 0.01 | 0.04 |
| fill | 0.04 | 0.11 | 0.02 | 0.08 |
| export | 0.03 | 0.08 | 0.03 | 0.06 |

같은 PC에서도 실행마다 차이가 커서(같은 쿼리 0.8~1.3초) 소수 둘째 자리는 의미가 작다.

### 바꾼 것

- 방문자 수: `count(DISTINCT visitor_id)` → `SELECT count(*) FROM (SELECT DISTINCT ...)`.
  `count(DISTINCT)`는 100만 행을 정렬하며 work_mem(4MB)을 넘겨 디스크(29MB)를 썼다. 하위 쿼리는 해시로 지운다.
  summary 366일 최악 1.08초 → 0.32초
- daily: 표를 두 번 읽던 것을 한 번 읽어 (날짜, 방문자)로 묶은 뒤 날짜로 다시 합치도록.
  같은 CTE를 두 번 참조하면 PostgreSQL이 100만 행을 임시 저장해 오히려 느려졌다(1.92초).
  DB 시간 최악 1.19초 → 0.95초, 현실 0.52초 → 0.34초
- 한국 날짜: `AT TIME ZONE 'Asia/Seoul'` → `+ 9시간` 고정 (서머타임 없음, `utils/date-range.ts`와 같은 방식)

결과가 바뀌지 않은 것은 두 가지로 확인했다.
최악 분포 데이터에서 바꾸기 전·후 응답(summary·daily × 기본·366일·하루)이 바이트 단위로 같았다.
또 `tests/admin-stats.test.ts`가 +9시간이나 DISTINCT를 망가뜨리면 실패하는 것도 확인했다.

### 남은 것

- 최악 분포의 daily 366일은 1.33초로 목표를 넘는다. 실제로는 방문 한 번에 이벤트가 여러 개라 현실 분포에 가깝다
- 1년에 이벤트가 수백만 건을 넘으면 날짜별 집계 테이블(밤마다 전날 분을 계산)을 둔다
