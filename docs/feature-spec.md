## 2. 1단계 설계(phase1-design.md)와 대조

| 항목 | 1단계 설계 | 실제 프론트 | 판정 |
|---|---|---|---|
| 피드백 저장 | `POST /feedback` | web: 구글폼 / 프로토타입: 버튼 제거 | 프로토타입 방향이면 **호출할 화면이 없음**. 유지할지 팀 결정 |
| 서식 번호 | `form_id` 숫자 1~999 | web: 숫자(출생신고서 = 4) / 프로토타입: 문자열 `birth-report` | **안 맞음**. 공통 서식 식별자를 정해야 함 |
| 이용 이벤트 종류 | web GA4 이벤트 9종 | 프로토타입 행동(작성 시작·칸 열기·완성 보기·PNG 저장·인쇄·초기화)은 없음 | **빠짐**. 작성 도우미 이벤트 추가 필요 |
| 칸 단위 신고 | 서식 단위(`form_id`)까지만 | 프로토타입은 칸마다 안내 문구가 있어 "이 칸 안내가 이상해요"가 자연스러움 | **빠짐**. `feedback.field_id` 추가 |
| 입력값 저장 | 설계에 없음 | 프로토타입은 브라우저에만 저장 | 맞음. **서버로 받지 않는다**를 원칙으로 명시 |
| 관리자 통계 | 조회·다운로드·검색 | 작성 완료율(시작 대비 완성) 없음 | **빠짐**. 작성 도우미 퍼널 통계 추가 |
| GA4 | 유지 + 병행 | web만 있음 | 프로토타입도 병행할지 결정 |

## 3. 고칠 설계 (확정 전 제안)

1. **서식 식별자**: 문자열 `form_key`로 통일 (예: `birth-report`). web의 숫자 id는 `form_no`로 같이 둔다 (출생신고서 = 4). 두 프론트가 같은 서식을 같은 값으로 보냄
2. **피드백**: `field_id`(칸 id, 예: `childNameKo`) 컬럼 추가. 유형 `guide`(칸 안내 오류) 추가
3. **이벤트 종류 추가**: `fill_start`, `field_open`, `fill_preview`(완성 서식 보기), `fill_png_save`, `fill_print`, `fill_reset`. 값(입력 내용)은 절대 안 보내고 `form_key`·`field_id`·언어만
4. **통계 추가**: `/admin/stats/fill?from=&to=` — 서식별 작성 시작·완성 보기·저장/인쇄 수, 칸별 안내를 많이 연 순위(어려운 칸 찾기)

## 4. 지킬 원칙

- 서식에 적는 값(이름·주민등록번호·주소 등)은 서버로 보내지도 저장하지도 않는다. 지금 프로토타입처럼 브라우저에만 둔다
- "다른 기기에서 이어 쓰기" 같은 요청이 와도 주민등록번호를 서버에 두는 일이라 별도 검토(동의·암호화·보관 기간) 없이 하지 않는다

## 5. 백엔드 범위 정리 (단계별)

| 단계 | 내용 | 상태 |
|---|---|---|
| 1단계 | 피드백(칸 단위 포함) + 이용 통계(작성 도우미 포함) + 관리자 토큰 | 설계 초안, 위 3절 반영 필요 |
| 2단계 | 번역·안내 오류 신고 화면 (프론트) | 1단계 테이블 재사용 |
| 3단계 | 서식 데이터 DB 이전(web 41종 + 작성 도우미 칸 정의), 이미지 업로드, 관리자 로그인 | 미설계 |

## 6. 팀 결정이 필요한 것

1. v2는 프로토타입(작성 도우미) 방향인가, 기존 41종 안내를 합치는가
2. v2에서 피드백을 다시 넣는가 (프로토타입은 뺐음)
3. v2에서 이용 분석(GA4 또는 우리 서버)을 넣는가
4. 공통 서식 식별자 (`form_key` 문자열 제안)
